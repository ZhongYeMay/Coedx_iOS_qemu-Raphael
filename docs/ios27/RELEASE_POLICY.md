# 发布规则 / Release policy

每个经测试的、有意义的小进展发布一个新的预发布版本，例如
`v0.3.0-pre.1`、`v0.3.0-pre.2`。每次发布必须说明变更、测试范围、已知限制，
并提供源码提交、测试日志和附件 SHA-256。不覆盖既有 Release，不静默移动已发布标签。

大进展通过可重复的实际运行验证后，才发布正式版。iOS 27 的首个启动里程碑至少需要：
明确的固件版本/构建号/设备、QEMU 固定源码提交与构建命令、宿主环境、固件哈希（不含固件本身）、
完整串口日志，以及重复的内核、launchd、root shell 验证。桌面里程碑还需要
SpringBoard 显示与输入交互的可复现证据。命令行成功不等于桌面成功，更不等于 GPU 加速。

当前工作流只允许预发布；正式版必须等运行证据及对应审核门禁落实，不能只改布尔值绕过。
发布说明必须准确指明通过的是哪个里程碑，不能把环境检查或编译成功标成系统启动成功。

## 操作流程

在 `ios27-development` 分支更新代码、测试和发布说明，然后递增
`releases/ios27.json` 的版本。该文件的提交触发测试、打包、生成校验值、创建草稿，
附件上传成功后才公开为预发布版。测试失败则不发布；已存在的标签或 Release 不覆盖。
该流程不下载 Apple 固件、不启动 iOS，也不会将开发分支自动合并到 main。

这是由提交触发的发布自动化，不是无人值守的持续开发服务。
